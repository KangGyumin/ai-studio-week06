# 프롬프트 3기법 비교 리포트

## 1. 과업 정의

- 선택: 고객 문의 분류  
- 분류 항목: 주문 / 배송 / 환불 / 제품문의 / 기타  
- 긴급도 기준:  
  - 긴급도 3 (즉시 개입): 안전 문제, 파손/오배송, 법적 조치 언급, 강한 감정이 섞인 클레임 및 즉각 환불 요구.
  - 긴급도 2 (빠른 처리): 방치 시 클레임으로 발전할 수 있는 이슈. 배송 지연 확인, 발송 전 주문 옵션 변경 및 단순 취소.
  - 긴급도 1 (일반 안내): 단순 정보 제공으로 해결되는 문의. 재입고 일정, 사이즈/성분 문의, 플랫폼 이용 방법.
- 출력 형식: {"type": ..., "urgency": ...}

## 3. 프롬프트 전문

### Zero-shot

```
당신은 고객 문의 분류기입니다.
고객의 문의를 다음 기준에 따라 분류하고 긴급도를 판정하세요.

[분류 항목]
주문, 배송, 환불, 제품문의, 기타

[긴급도 기준]
3: 즉시 개입 (안전 문제, 파손/오배송, 법적 조치 언급, 강한 감정이 섞인 클레임 및 즉각 환불 요구)
2: 빠른 처리 (방치 시 클레임 발전 가능, 출고 전 변경, 배송 지연)
1: 일반 안내 (단순 정보 제공, 재입고, 사이즈 문의)

[출력 규칙]
반드시 아래 JSON 형식으로만 응답하세요. 다른 설명이나 텍스트를 절대 포함하지 마세요.
{"type": "분류항목", "urgency": 긴급도숫자}

입력 문장: {입력 문장}
```

### Few-shot

```
당신은 고객 문의 분류기입니다.
고객의 문의를 다음 기준에 따라 분류하고 긴급도를 판정하세요.

[분류 항목]
주문, 배송, 환불, 제품문의, 기타

[긴급도 기준]
3: 즉시 개입 (안전 문제, 파손/오배송, 법적 조치 언급, 강한 감정이 섞인 클레임 및 즉각 환불 요구)
2: 빠른 처리 (방치 시 클레임 발전 가능, 출고 전 변경, 배송 지연)
1: 일반 안내 (단순 정보 제공, 재입고, 사이즈 문의)

[출력 규칙]
반드시 아래 JSON 형식으로만 응답하세요. 다른 설명이나 텍스트를 절대 포함하지 마세요.

[예시]
입력: 비회원으로 구매했는데, 주문 내역은 어디서 확인하나요?
출력: {"type": "주문", "urgency": 1}

입력: 어제 발송됐다고 알림톡이 왔는데, 아직도 운송장 조회가 안 됩니다.
출력: {"type": "배송", "urgency": 2}

입력: 결제가 두 번 됐어요! 카드값 이중청구된 것 같아요. 급합니다.
출력: {"type": "주문", "urgency": 3}

입력 문장: {입력 문장}
출력:
```

### CoT

```
당신은 고객 문의 분류기입니다.
고객의 문의를 다음 기준에 따라 분류하고 긴급도를 판정하세요.

[분류 항목]
주문, 배송, 환불, 제품문의, 기타

[긴급도 기준]
3: 즉시 개입 (안전 문제, 파손/오배송, 법적 조치 언급, 강한 감정이 섞인 클레임 및 즉각 환불 요구)
2: 빠른 처리 (방치 시 클레임 발전 가능, 출고 전 변경, 배송 지연)
1: 일반 안내 (단순 정보 제공, 재입고, 사이즈 문의)

[출력 규칙]
아래 추론 단계를 거쳐 단계별로 생각한 뒤, "마지막 줄"에만 최종 JSON을 출력하세요.
마지막 줄의 JSON 출력은 반드시 {"type": "분류항목", "urgency": 긴급도숫자} 형태여야 합니다.

[추론 단계]
1단계: 문의 문장에서 표면적인 원인과 고객의 '최종 요구 목적'을 명확히 분리하여 파악한다. 반어법이 쓰였는지도 확인한다.
2단계: 파악한 최종 목적을 바탕으로 가장 적합한 분류 항목(type)을 하나 결정한다.
3단계: 안전, 파손, 감정적 표현, 시간 제한 여부를 분석하여 긴급도(urgency) 1~3 중 하나를 판정한다.

입력 문장: {입력 문장}
```

## 6. 분석

- **형식 준수:**
  - **Zero-shot / Few-shot:** 코드펜스나 사족 없이 단일 JSON만 출력되어 즉시 `json.loads()` 파싱 가능(O).
  - **CoT:** 약속대로 마지막 줄에 JSON을 출력하여 파싱은 가능했으나(O), 백엔드에서 마지막 줄을 슬라이싱하는 전처리 코드가 필수로 요구됨.

- **분류 정확성 (특히 애매 사례에서):**
  - **수렴 현상:** 단문 문의 특성상 모델의 기본 문맥 파악 능력이 충분하여, 4번(환불)과 5번(배송) 등 애매한 의도도 세 기법 모두 동일하게 정답을 도출함.
  - **불일치 사례 (1번, 3번):**
    - **1번:** 모델은 단순 배송 조회 안내로 해석하여 긴급도 1로 판단(인간 정답은 2).
    - **3번:** 모델은 '주소 변경'을 주문 카테고리로 보고, 프롬프트에 명시된 "출고 전 변경: 2" 규칙을 인간 직관보다 엄격하게 기계적으로 적용함(`주문/2`).

- **일관성:**
  - 애매 사례(4번)를 3회 반복 실행한 결과, 세 기법 모두 3회 내내 `{"type": "환불", "urgency": 3}`을 100% 동일하게 출력하여 웹 UI 환경에서도 매우 안정적인 결정론적 결과를 보임.

- **비용:**
  - **Zero-shot / Few-shot:** 불필요한 추론 없이 최종 JSON만 짧게 출력하므로 토큰 소모가 적고 경제적임. (Few-shot은 예시가 추가된 만큼 입력 토큰이 소폭 늘어나지만 출력 토큰은 최소화됨)
  - **CoT:** JSON 외에 1~3단계의 긴 추론 과정을 모델이 직접 생성하므로, 단가가 더 비싼 출력 토큰을 불필요하게 많이 소모함. 대량 분류 파이프라인에는 비효율적임.

## 7. 결론 — 우리 팀이 쓸 기본 전략

- **선택 기법:** **Few-shot Prompting (경계 사례 예시 2~3건 포함)**
- **채택 근거:**
  1. **가성비와 응답 속도:** 단순 문의 분류 과업에서 CoT의 정확도 향상 이득은 미미한 반면, 출력 토큰 비용과 지연 시간(Latency) 부담이 과도함.
  2. **형식 안정성 극대화:** Zero-shot의 잠재적 사족 발생 위험을 차단하고, 모델이 정답 JSON 구조를 직접 모방하게 하여 백엔드 파싱 성공률을 보장함.
  3. **경계 케이스 사전 제어:** '원인-요청 충돌'이나 '출고 전 변경' 같은 까다로운 경계 케이스 2~3건을 예시로 제공함으로써 도메인 규칙을 즉각 학습시킬 수 있음.
- **기본 파이프라인 아키텍처:**
  - *"Few-shot 프롬프트를 기본으로 채택하되, LLM 출력을 믿을 수 없는 외부 입력으로 간주하고 백엔드에 3중 방어 로직(마크다운 정규화 → `json.loads()` 예외 처리 → 카테고리 유효성 검증)을 결합하여 시스템 안정성을 구축한다."*

## 8. AI 사용 기록

### [기록 1] 과제 1 리포트 분석 프레이밍 및 테스트 케이스 설계
* **구조화 질문 (5요소 템플릿):**
  1. **맥락(Context):** AI 오케스트레이션 6주차 과제로, LLM을 통제 가능한 부품으로 다루기 위해 문의 분류 과업을 3개 프롬프트 기법(Zero/Few/CoT)으로 비교 실험 중임.
  2. **목표(Goal):** 고객 문의를 5개 항목(주문/배송/환불/제품문의/기타)으로 분류하고 긴급도(1~3)를 판정하는 테스트 입력 5건(명확 3건, 애매 2건) 및 3기법 프롬프트를 설계함.
  3. **제약 조건(Constraints):** 견본 파일의 문장을 그대로 복사하지 말 것, 실명·전화번호 등 PII를 배제할 것, 동일한 JSON 스키마를 출력하도록 강제할 것.
  4. **입력 자료(Input):** 견본 파일의 라벨 구조와 긴급도 기준 정의.
  5. **출력 형식(Output):** Markdown 표 형식의 테스트 케이스 목록 및 프롬프트 전문 3종.
* **AI 답변 요지:** 
  - 명확 3건(단순 배송 조회, 스펙 문의, 긴급 주소 변경)과 애매 2건(원인-요청 충돌, 반어법 클레임) 후보 문장 생성.
  - 동일한 JSON 스키마(`{"type": ..., "urgency": ...}`)를 요구하는 프롬프트 3종(Zero-shot, Few-shot, CoT) 구조 제안.
* **채택 / 기각 판단:** **부분 채택 및 수정**
  - AI가 제안한 문장 중 애매 사례 2건(일주일 배송 지연 환불 요청, 파손 반어법)의 모호성이 실험에 적합하여 채택함.
  - 내 정답 설정 시 3번(출고 전 주소 변경)의 긴급도를 AI 제안(2) 대신 즉각 대응이 필요한 '3'으로 직접 수정 확정함.
* **검증 결과:** 무료 챗봇 UI에서 21회 실행 결과, CoT는 프롬프트 규칙대로 마지막 줄에 JSON을 분리 출력함을 확인함.

### [기록 2] 분석 리포트 비용 항목 검증 및 문장 설명 요구 (코드/문장 검증)
* **구조화 질문 (5요소 템플릿):**
  1. **맥락(Context):** 무료 챗봇 웹 UI에서 실험하여 실제 토큰 수가 화면에 표시되지 않는 환경임.
  2. **목표(Goal):** 리포트 6번의 '비용' 분석 문장에서 토큰 소모량과 API 과금 관점의 차이를 기술하고, 내가 수정한 문장이 강의의 토큰/비용 개념에 부합하는지 설명 및 검증을 요청함.
  3. **제약 조건(Constraints):** 측정되지 않은 임의의 토큰 숫자를 쓰지 말 것, 입력 토큰과 출력 토큰의 단가 차이 개념을 포함할 것.
  4. **입력 자료(Input):** "Zero-shot은 입출력이 최소화되고, CoT는 1~3단계 추론으로 인해 단가가 비싼 출력 토큰 소모가 커 대량 파이프라인에 비효율적이다."
  5. **출력 형식(Output):** 내가 작성한 문장의 논리적 타당성 설명 및 간결한 교정안.
* **AI 답변 요지:** 
  - 작성한 문장이 강의의 핵심 개념(출력 토큰 단가 > 입력 토큰 단가, 추론 토큰에 따른 비용 급증)을 정확히 짚고 있음을 확인하고, 웹 UI 환경에 맞게 임의의 숫자를 배제한 정성적 서술로 정돈해 줌.
* **채택 / 기각 판단:** **채택**
  - 불필요한 추정 수치를 걷어내고 정성적 비교로 정리한 수정본을 리포트에 반영함.
* **본인의 검증 의견:** 
  - AI의 피드백대로 실제 웹 UI 테스트에서는 토큰 수치를 증명할 수 없으므로, 정성적 개념(출력 토큰 오버헤드)으로 기술하는 것이 감점 요인을 방지하고 강의 취지에도 부합함을 검증함.
